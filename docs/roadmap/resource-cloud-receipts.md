## 当前已实现基线

[封面云端实现](metadata-cover-cloud-storage.md) 已支持 BaiduPCS-Go 与 rclone Google Drive，两个后端各完成 20 张歌手图、20 张专辑图上传、内容核验及数据库回写。当前每条资源只有一组 cloud_*，保存最后确认的云端回执；cloud_backend 的值为上传实现 baidupcs/rclone，不代表实际存储平台。切换后端会替换同一行的最后回执，不表示之前的远端对象已删除。

上述现状属于本次 PR；下述结构、字段、增量任务及大规模性能验证均为下一阶段方案，不能表述为已经支持双端回执或已经完成 SQL 迁移。

## 已确认的设计

- song_resources、singer_resources、album_resources 继续负责本地资源任务、文件快照、下载认领和错误；云端路径、回执快照、上传状态、时间、云端认领和错误迁入独立 resource_cloud_receipts 表。
- 一张回执表共同保存百度和 Google，每个资源、每个平台一条当前记录，不按平台建两张表，不把多个平台回执塞入 JSON。
- cloud_provider 使用 baidu/gdrive，标识实际存储平台。baidupcs/rclone 继续作为运行时上传适配器配置，不作为持久化平台身份或对外回执字段。
- 资源归属必须携带 owner_type（song/singer/album）和 resource_id，联合 cloud_provider 唯一，不能假设三张资源表的数字主键全局唯一。实际 DDL 还须明确跨资源表的引用完整性、级联删除和别名归一策略，不能给多态 resource_id 直接声明指向三表的单一外键。
- 每端独立保存状态、路径、大小/SHA-256、上传时间、认领代次/批次/时间、脱敏错误及必要意图。重试更新当前记录，详细尝试历史继续进入现有批次和事件。
- 成功且匹配资源当前文件快照才表示当前副本已确认；本地刷新、资源删除、专辑别名合并、取消和 stale 恢复均需同步维护各端回执，保留代次和文件快照条件确认。
- 暂不引入 target_id、多盘/多账号编排。更换实际账号或盘时须显式使旧目标的回执失效并重新核验，不能因 remote 别名相同而沿用旧结果。
- 当前落地方案不在 resources 重复持久化 baidu_stored/gdrive_stored。API 可从回执派生这些判断字段；后续仅在实际查询负载及压测证明收益后，再评估可重建的摘要缓存及其事务一致性。

## 平台识别与历史数据迁移

新增 migration，先建表、迁入并核对旧回执、切换全部读写与绑定，最后删除 resources 的旧云端列。不改写已经执行的 V2026102802、V2026102901 或 main 已合入的历史迁移；开始实施时重新核对编号。

baidupcs 的已确认回执可以映射为 baidu；rclone 只能依据明确的平台配置或已核实的 remote 类型识别平台，不能按 remote 名称猜测为 Google。已验证的本次 Google 回执可回填 gdrive，其他不明记录保留待核对，不伪造平台或成功状态。不能仅从最后一份回执推断另一端也已上传，需凭独立证据或重新核验补齐。

联动范围包括三类资源模型、存储 port/adapter、组合根、SQL/查询、上传意图、队列/幂等/提交不确定核对、恢复及别名迁移、DTO、API 清单和两份 OpenAPI、结构快照及 schema 状态和相关测试。接口中的 backend 语义替换为 provider，并明确协议兼容处理；上传工具选择配置继续有效。

## 大规模运行与验证条件

不能依据当前测试库行数推断长期性能。容量按独立文件资源数计算：多个音质、歌词、封面分别占资源；两个平台的当前回执至多约为资源数的两倍，重试不追加当前回执行。

- 日常采用增量任务：本地文件确认时，在同一事务创建已启用平台的待处理记录；刷新使相关记录重新待处理。worker 从 provider、owner_type、状态匹配的索引领取有界任务，避免每轮全量关联资源表寻找遗漏。
- 点查/分页按资源身份批量读取回执，避免逐条查询；唯一索引和队列索引按实际过滤与排序设计。
- 历史回填、缺失记录发现和完整对账使用可续跑的游标分批遍历，定期执行；全量精确盘点不承诺即时完成。
- 数据库回执表示上次确认，远端文件是否仍存在须独立清单对账；大规模精确计数可评估增量汇总并定期校准。
- 性能验收至少覆盖千万级资源、两千万级回执，模拟绝大多数已完成、少量待处理、失败重试及并发刷新，报告延迟分位数、扫描行数、锁等待、冷/热缓存及索引/数据体积。用 EXPLAIN ANALYZE 核对实际计划；同负载对比是否需要资源摘要缓存。上述压测尚未执行。

设计依据：[MySQL 联合索引](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[EXPLAIN ANALYZE](https://dev.mysql.com/doc/refman/8.0/en/explain.html)、[InnoDB 计数行为](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html#function_count)。这些文档提供优化依据，不构成本项目长期吞吐或延迟的实测证明。
